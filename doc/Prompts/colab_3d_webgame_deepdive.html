// 01

DAS GRUNDPROBLEM

Google Colab ist primär als Python/ML-Umgebung konzipiert. Es gibt keinen nativen Browser, kein Display-System und keinen exponierten Port nach außen. Ein 3D-Webgame braucht aber genau das: GPU-beschleunigtes WebGL-Rendering im Browser, einen Dev-Server mit öffentlichem Endpunkt und stabile Session-Laufzeiten.

Problem 1: Kein sichtbares Display

Colab läuft headless auf einer Linux-VM ohne X11 Desktop. WebGL benötigt aber einen GL-Kontext, der entweder an ein echtes Display oder ein virtuelles Framebuffer-Device gebunden ist.

Problem 2: Kein offener Port

Colab-VMs sind hinter Google-Firewall. localhost:3000 (Vite Dev Server) ist von außen nicht erreichbar — Tunneling ist zwingend notwendig.

Problem 3: Falsche GPU-Treiber

Standardmäßig sind die Linux-Treiber nicht für Vulkan/GL-Rendering konfiguriert. Headless Chrome erkennt die NVIDIA T4 nicht auf GL_RENDERER-Ebene ohne manuellen Treiberfix.

Problem 4: Session-Timeout

Colab Free: max. 12h Inaktivitäts-Timeout, GPU-Sessions oft kürzer (~3h). Kein persistenter Server — nur für Dev & Testing geeignet, nicht für Production.

DER RENDERING-STACK

Für ein 3D-Webgame in Colab gibt es drei konzeptionell verschiedene Rendering-Ansätze. Alle haben unterschiedliche Anforderungen und Trade-offs.

Ansatz A: Headless-Chrome + WebGL

Konzept: Chromium läuft headless auf der Colab-VM mit aktivierter GPU-Beschleunigung via Vulkan-Backend. Das 3D-Rendering passiert serverseitig im Browser — Frames können per Screenshot oder Video-Stream extrahiert werden.

Eignung: Testing, Screenshots, automatisiertes Rendering

Nicht geeignet für: Echtzeit-Interaktion mit Spieler

Ansatz B: Vite Dev Server + Tunnel

Konzept: Der 3D-Webgame-Code läuft als statischer Vite-Dev-Server auf der Colab-VM. Der Browser-Client (User's PC) rendert WebGL lokal. Colab liefert nur den Code und ggf. Game-State via WebSocket.

Eignung: ✅ Empfohlen für interaktives Development

GPU-Last: Läuft auf dem Client-Browser, nicht auf Colab-GPU

Ansatz C: Pixel-Streaming (Server-Side Render)

Konzept: Die gesamte 3D-Szene wird auf der Colab-VM gerendert (GPU-beschleunigt via VirtualGL) und als Video-Stream (MJPEG/WebRTC) an den Client übertragen. Client braucht keine GPU.

Eignung: Hochauflösendes Rendering auf schwacher Client-Hardware

Nachteil: Latenz, Bandbreite, Colab-Session-Limits

Für Corona Control V4 ist Ansatz B die pragmatischste Lösung: Colab hostet den Build-Server, der Client-Browser rendert WebGL lokal. Ansatz C ist relevant wenn schwache Client-Hardware (z.B. kein GPU) das Ziel ist.

GPU SETUP & CHROME FLAGS

Das korrekte Setup von Headless Chrome mit Hardware-GPU-Beschleunigung auf einer Colab T4-Instanz erfordert spezifische Flags und Treiber. Hier der komplette, getestete Setup-Flow:

01
Runtime-Typ wählen

In Colab: Runtime → Change runtime type → Hardware accelerator: T4 GPU. Die VM wird mit angebundener NVIDIA T4 gestartet.

02
Korrekte NVIDIA-Treiber installieren

Die Default-Treiber erkennen die T4 nicht korrekt auf Vulkan-Ebene. libnvidia-gl-525 + vulkan-tools beheben das.

03
Chromium + Puppeteer installieren

Puppeteer bringt eine kompatible Chromium-Version mit. Alternativ: System-Chromium via apt-get. Node.js muss vorher installiert sein.

04
Chromium mit Vulkan-Flags starten

Die kritischen Launch-Args für GPU-beschleunigtes WebGL/WebGPU in Headless Chrome auf Linux/Colab.

05
GPU-Status via chrome://gpu verifizieren

Zielzustand: "WebGL: Hardware accelerated", "Vulkan: Enabled". Ohne GPU-Beschleunigung ist das Rendering 10–50x langsamer.

const browser = await puppeteer.launch({
  headless: 'new',
  args: [
    '--no-sandbox',
    '--headless=new',

vite.config.ts — Colab-kompatible Konfiguration 
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  server: {
    host: '0.0.0.0',   // Alle Interfaces (für Tunneling)
    port: 3000,
    strictPort: true,
    cors: true,
    hmr: {               // HMR über Tunnel (wichtig!)
      clientPort: 443,
      protocol: 'wss'
    }
  },
  optimizeDeps: {
    include: ['three', '@react-three/fiber', '@react-three/drei']
  }
})
// HMR über Tunnel: Fallstrick Hot Module Replacement (HMR) kommuniziert über WebSocket. Bei Tunneling (Cloudflare/ngrok) muss HMR explizit auf clientPort 443 und protocol 'wss' gesetzt werden, sonst schlägt die WS-Verbindung fehl und du bekommst keine Live-Updates.

Alternativ zu Vite kann auch ein einfacher Python HTTP-Server verwendet werden, wenn das Projekt bereits gebuildet ist:

TUNNELING DEEP DIVE

Da Colab-VMs keine öffentlich erreichbaren IPs haben, ist Tunneling der einzige Weg, einen auf Colab laufenden Server von außen zugänglich zu machen. Drei Hauptoptionen stehen zur Verfügung.

Service Account nötig? Free HTTPS? WebSocket? Stabilität Empfehlung
Cloudflare Tunnel
(cloudflared)		 Nein (zero-trust free) ✅ Ja ✅ Ja SEHR GUT ⭐ Empfohlen
ngrok Ja (free tier) ✅ Ja ✅ Ja GUT 2. Wahl
Pinggy Nein ✅ Ja ✅ Ja MITTEL Backup
Colab Native Proxy Google Account ✅ Ja ⚠️ Limitiert EINGESCHRÄNKT Nur Dateien

Option 1: Cloudflare Tunnel (empfohlen)

cloudflared erstellt einen sicheren Tunnel von der Colab-VM zu Cloudflares Edge-Netzwerk. Kein Account nötig für temporäre URLs (trycloudflare.com-Domain). Unterstützt HTTPS + WebSocket nativ.

CLOUDFLARE TUNNEL SETUP

!wget -q https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64 -O cloudflared
!chmod +x cloudflared

# Tunnel starten (Port 3000 → öffentliche URL)
!./cloudflared tunnel --url http://localhost:3000 > /tmp/cf.log 2>&1 &

# Warten + URL extrahieren

with open('/tmp/cf.log') as f:
    log = f.read()
    urls = re.findall(r'https://[a-z0-9\-]+\.trycloudflare\.com', log)
    if urls:
        print(f"🌐 PUBLIC URL: {urls[0]}")
    else:
        print(log)  # Debug output

WebSocket-Tunneling für Game-State

Wenn dein Spiel FastAPI WebSockets für NPC-State, Multiplayer o.ä. verwendet, muss der WS-Port separat getunnelt werden — oder du verwendest denselben Port (Vite-Proxy-Config auf /ws).

Vite Proxy + FastAPI WebSocket

server: {
  proxy: {
    '/ws': {
      target: 'ws://localhost:8000',
      ws: true,
      changeOrigin: true
    },
    '/api': {
      target: 'http://localhost:8000',
      changeOrigin: true
    }
  }
}

PIXEL STREAMING: SERVER-SIDE RENDER

Wenn das Rendering vollständig auf Colab-GPU stattfinden soll (kein Client-GPU nötig), kommt Pixel-Streaming via VirtualGL + TurboVNC + MJPEG/WebRTC ins Spiel. Das ist komplexer, aber ermöglicht z.B. Hochqualitäts-Rendering auf einem einfachen Smartphone-Browser.

COLAB VM (GPU)
│
Xvfb :99 (Virtual Display)
│
VirtualGL (GL → GPU via DRI)
│
Chromium + Three.js (rendern auf :99)
│
FFmpeg MJPEG Stream (Port 8080)
│
Cloudflare Tunnel
│
CLIENT BROWSER (kein GPU nötig)
XVFB + VIRTUALGL SETUP 
# System-Deps für virtuelles Display
!apt-get install -y xvfb x11-utils virtualgl ffmpeg

# Xvfb starten (virtuelles Display :99)
!Xvfb :99 -screen 0 1920x1080x24 &
import os; os.environ['DISPLAY'] = ':99'

# Chromium mit VirtualGL starten (OpenGL → GPU)
!vglrun chromium-browser \
  --no-sandbox \
  --use-gl=desktop \
  --display=:99 \
  http://localhost:3000 &

# Screen als MJPEG-Stream via FFmpeg
!ffmpeg -f x11grab -r 30 -s 1920x1080 \
  -i :99 -vcodec mjpeg -q:v 3 \
  -f mpjpeg http://0.0.0.0:8080/stream &
VirtualGL

Leitet OpenGL-Aufrufe von einer X11-Session (Xvfb) auf den echten GPU-Treiber um. Ohne VirtualGL würde Chromium auf dem Xvfb Software-Mesa-Renderer fallen — viel langsamer.

Xvfb

X Virtual Framebuffer: Stellt ein virtuelles Display bereit, ohne echten Monitor. Chromium braucht für headless WebGL-Rendering mit vollen GPU-Features manchmal eine X11-Verbindung.

WebGPU + Xvfb

WebGPU (via Dawn/Vulkan/SwiftShader) schlägt häufig ohne X11-Display-Connection fehl. Wenn WebGPU gebraucht wird: immer xvfb-run nutzen. Chrome 124+ benötigt explizite Vulkan-Flags.

remocolab: All-in-One Lösung

Das Open-Source-Projekt remocolab automatisiert den kompletten VNC+SSH+VirtualGL-Stack auf Colab mit einem Einzeiler:

REMOCOLAB (VNC + GPU + Tunnel) 
!pip install git+https://github.com/demotomohiro/remocolab.git
import remocolab
remocolab.setupVNC(tunnel="argotunnel")
# Oder mit ngrok:
remocolab.setupVNC(tunnel="ngrok", ngrok_region="eu")

Danach: TurboVNC-Client auf PC → SSH-Tunnel öffnen → VNC-Session → Vollständiger Linux-Desktop mit GPU-beschleunigtem Browser. Für 3D WebGL-Development die mächtigste Setup-Option.

# server.py schreiben
server_code = """
from fastapi import FastAPI, WebSocket
from fastapi.middleware.cors import CORSMiddleware
import uvicorn, asyncio

app = FastAPI()
app.add_middleware(CORSMiddleware, allow_origins=["*"])

npc_state = {}  # Game State Store

@app.websocket("/ws/npc")
async def npc_websocket(ws: WebSocket):
    await ws.accept()
    while True:
        data = await ws.receive_json()
        npc_state.update(data)
        await ws.send_json(npc_state)

if __name__ == '__main__':
    uvicorn.run(app, host='0.0.0.0', port=8000)
"""

with open('/content/game/server.py', 'w') as f:
    f.write(server_code)

# FastAPI im Hintergrund

  ['python', 'server.py'],
  cwd='/content/game'
